# API development (City of Asheville)

Help developers design, build, review and maintain HTTP APIs that follow City conventions. The
OpenAPI document is the contract: change it first, then the code.

## Ground rules (always)

- **Spec first.** Every API change starts in `openapi.yaml` and is reviewed there. Code, types and
  tests follow the spec, never the other way round.
- **Ask, don't assume,** for anything in [Questions to ask](#questions-to-ask). Never invent
  account IDs, bucket names, ARNs, hostnames or project names. Leave a clear `<PLACEHOLDER>`.
- **No sensitive data** in specs, examples, test data, logs or commits: no resident PII,
  credentials, tokens, internal hostnames/IPs or real account IDs. Secrets live only in AWS Secrets
  Manager or SSM Parameter Store.
- **Public records:** API code, specs, logs and data may be public records (N.C.G.S. §132).
- **Humans deploy.** Run checks freely, but don't run `terraform apply` (or anything that changes
  AWS) unless the developer explicitly asks, and never against `prod` without their confirmation.
- **Disclose AI use** in PR descriptions, and tell the developer to verify generated code and specs.

## City defaults

| Area | Default |
|---|---|
| Stack | TypeScript + Express 5 on the newest Node.js LTS that Lambda supports (check the Lambda runtimes page) |
| Contract | OpenAPI **3.0.x**, one `openapi.yaml` at the API root, linted with Spectral's `spectral:oas` ruleset |
| Enforcement | Types generated by `openapi-typescript` (committed). Requests validated at runtime by `express-openapi-validator`, responses validated in contract tests |
| Hosting | AWS Lambda + **AWS Lambda Web Adapter** (unchanged Express server), behind an **API Gateway HTTP API** built from the spec |
| Infra | Terraform/OpenTofu ≥ 1.10. Modules first (the infrastructure-as-code team's, then public registry). S3 state with `use_lockfile = true`, key `terraform/<project-name>/<dev\|prod>/terraform.tfstate`, region `us-east-1` |
| Auth | Internal: **AWS IAM (SigV4)** at the gateway. Public: anonymous + throttling. No other auth schemes without the developer's decision |
| URLs | `/v1/...` major version prefix. **kebab-case** paths, plural nouns |
| JSON | **snake_case** fields and query params, RFC 3339 UTC timestamps (`*_at`) |
| Errors | **RFC 9457 Problem Details** (`application/problem+json`), no stack traces or internal messages |
| Lists | **Cursor** pagination by default (`limit`, `cursor` → `{data, next_cursor}`). Offset only for small or relational data |
| Ops | Structured JSON logs with request ID, no PII. `GET /v1/health` |
| Tests | Vitest unit tests, contract tests against the spec, `oasdiff` breaking-change check vs. the base branch |

Details: [references/conventions.md](references/conventions.md).

## Questions to ask

Ask before scaffolding or before changes that depend on them. Ask only the ones that matter for
the task.

1. Is the API **internal-only, public, or mixed**? Which operations are public?
2. For internal APIs: **which IAM roles or services** will call it?
3. **Data source:** PostgreSQL/RDS (PostGIS?), DynamoDB, or an existing City system?
4. **Repo layout:** standalone repo, or a subfolder of a monorepo or app repo?
5. **Throttling limits** for dev and prod. For public APIs: limits are shared by all callers, so
   is **CloudFront + AWS WAF** needed in front?
6. **Project name** (used in the state key) and the **Terraform state bucket** name (from the
   infrastructure-as-code team; never guess).
7. Which **infrastructure-as-code team Terraform modules** exist for Lambda, API Gateway and logging?
8. For deprecations: what **policy and notice period** apply to this API's consumers?

## Workflows

### Start a new API

1. Ask the questions above.
2. Copy this skill's `assets/starter/` folder to the target location (repo root or subfolder). Read
   its [README](assets/starter/README.md). If it's a subfolder, move `.github/workflows/api-ci.yml`
   to the repo root's `.github/workflows/` and set `API_DIR`.
3. Rename: `package.json` `name`, `info.title`/`description`/`contact` in `openapi.yaml`, and the
   `<PROJECT_NAME>` and `<STATE_BUCKET>` placeholders in `infra/` (leave the placeholder if
   unknown).
4. Check for newer versions before keeping the starter's pins: the Lambda Node.js runtime, the Lambda
   Web Adapter layer version, Terraform modules and npm dependencies. Upgrade only if `npm run check`
   and `terraform validate` still pass.
5. Replace the example `service-requests` resource with the real resources, spec first: follow
   **Add or change an endpoint**. Remove example code, data and tests you no longer need.
6. Wire the real data source ([references/data-access.md](references/data-access.md)) and auth
   ([references/aws-terraform.md](references/aws-terraform.md)).
7. Run `npm run check`, `npm run package` and `terraform -chdir=infra validate`. Hand deployment
   steps to the developer.

### Add or change an endpoint

1. Edit `openapi.yaml` following [references/openapi.md](references/openapi.md) and
   [references/conventions.md](references/conventions.md).
2. `npm run lint:spec`, then `npm run breaking` (or explain that CI runs it). If a change is
   breaking, stop and follow **Version and deprecate**.
3. `npm run gen:types`.
4. Implement the handler with the generated types
   ([references/express-lambda.md](references/express-lambda.md)).
5. Add unit and contract tests ([references/testing.md](references/testing.md)), then `npm run check`.
6. If you added an operation, decide its auth (IAM is the default; `security: []` makes it public)
   and mention the effect on callers' IAM policies.
7. Summarize the contract change for the PR description.

### Review an API or spec

Work through [references/review-checklist.md](references/review-checklist.md). Report findings
grouped by severity (blocker, should fix, suggestion), each with the location and a concrete fix.
Don't rewrite the API during a review unless asked.

### Version and deprecate

Follow [references/versioning-deprecation.md](references/versioning-deprecation.md): classify the
change, introduce `/v2` for breaking changes while `/v1` keeps working, and ask the developer for
the deprecation policy and dates before marking anything deprecated.

### Adopt an existing API

Follow [references/adopting-existing-apis.md](references/adopting-existing-apis.md): work within
the existing stack, capture its current behavior in a committed spec first, add checks, and apply
City conventions only to new versions. Don't rewrite stacks unless the developer asks.

## Commands (starter)

```bash
npm run dev          # local server on :8080
npm run check        # spec lint + generated types current + typecheck + tests (CI runs this)
npm run gen:types    # regenerate src/generated/openapi.ts after editing openapi.yaml
npm run breaking     # oasdiff vs origin/main (needs oasdiff installed)
npm run docs         # local API docs in .docs/ (not published)
npm run package      # lambda.zip for Terraform
terraform -chdir=infra init -backend=false && terraform -chdir=infra validate
```
